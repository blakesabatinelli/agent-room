# Spike 0.3: local file access for local and cloud agents

*Decision memo for D1. October 23, 2026. Prototype on `main` (commits a1234db, ed7cc73, 0239f14). Vendor facts were checked against vendor docs on Oct 23, 2026 (sources at the end); re-check before 1.1 starts.*

> **Update, Oct 23 (D9): Tailscale is a product requirement.** The recommendation below stands (hub MCP file tools by default), but the transport changes: agents on other devices reach the hub over the tailnet, and vendor-cloud agents reach only `/mcp` through Tailscale Funnel. The hosted relay and K5 (Fly.io) are withdrawn; `packages/relay` stays in the repo as a shelved fallback. Item 1.2 must still close points 1, 3, 4, 5 and 6 under "What 1.1 and 1.2 must fix"; points 2 and 7 (relay encryption and scale) no longer apply.

## Recommendation

**Relayed MCP file tools as the default, for every agent.** The hub is the only thing that touches the disk. Local CLI agents work in a per-task worktree (1.4); cloud agents reach granted folders through the hub's MCP tools over an outbound-only relay; writes arrive as diffs and apply only after approval. **Worktree sync** is kept for one case: heavy coding in a vendor's cloud sandbox (Claude Code on the web, Codex cloud), where the sandbox already clones from GitHub, so "sync" means pushing the task's worktree branch and merging the returned branch. **Vendor remote features** are not a foundation: each one serves only its own vendor.

This matches the leaning in `PRODUCT.md` 14. The prototype works end to end, and an independent security review judged it acceptable as a spike (not yet as product; see "What 1.1 and 1.2 must fix").

## The three options

| | A. Relayed MCP file tools (hub-mediated) | B. Worktree sync to the cloud sandbox | C. Each vendor's own remote features |
|---|---|---|---|
| **How** | Hub exposes `list_files`, `read_file`, `propose_file_write`, `file_write_status` over MCP. Cloud agents call them through an outbound relay; local agents call them on localhost | Hub creates a worktree per task, pushes it as a branch; the vendor's cloud sandbox clones it, works, pushes back; hub diffs and merges after approval | Claude Code Remote Control, ChatGPT Work's local executor, OpenAI Secure MCP Tunnel, Claude Desktop local MCP |
| **Security** | Best. One choke point: grants per room and agent, read and write separate, every write a reviewed diff, full audit. Nothing listens on the Mac | Good for code: the user's files never leave except as a branch the owner chose to push. Weak for non-repo folders (documents, decks), which would have to be uploaded wholesale | Mixed and per-vendor. Each has its own permission model the Room can't see or audit; no shared approval log |
| **Latency** | One tool call per file op. Measured overhead of the relay hop on loopback: +1.1 to 1.7 ms (3.5 ms direct vs 4.7 to 5.2 ms relayed, median of 20). Real cost is the internet round trip to the relay, roughly one RTT per call | One push and one pull per task (seconds), then local-speed work inside the sandbox. Best for many small edits | Native speed inside each vendor's own path |
| **Vendor coverage** | Every vendor that can call a remote MCP server: claude.ai custom connectors, ChatGPT developer-mode connectors, the OpenAI Responses API, the Claude Agent SDK, Codex CLI, Gemini CLI. Each needs a public HTTPS URL, which the relay provides | Only vendors whose cloud agents work from a git remote: Claude Code on the web, Codex cloud, Google Jules | One vendor each. No cross-vendor bridge exists |
| **Offline (Mac asleep or offline)** | Calls fail fast with 503 at the relay; the agent can retry or wait. Nothing is lost; pending writes wait for approval | The sandbox keeps working on its copy; the merge waits for the Mac | Varies; Remote Control and ChatGPT's executor need the computer online |
| **Works for non-code files** | Yes | Poorly | Varies |
| **Room keeps the audit and approvals** | Yes | Yes, at merge time | No |

**Why A wins:** it is the only option that covers every vendor, every kind of folder, and keeps the Room's own approvals and audit trail. B is a better transport for one workload, so it stays as the fallback for heavy cloud coding. C confirms the market gap: nothing bridges vendors.

## What the research changed

- **Cloud vendors need a public HTTPS MCP URL.** claude.ai custom connectors, ChatGPT developer-mode connectors and the Responses API all call the MCP server from the vendor's cloud. The relay gives the hub that URL (`https://<relay>/h/<hub-id>/mcp`) without opening a port on the Mac.
- **Auth differs by vendor.** claude.ai custom connectors accept OAuth, a static header or no auth; ChatGPT connectors expect OAuth. Item 1.2 therefore needs a small OAuth front on the hub's MCP endpoint (issue a per-agent, per-room, expiring token through an OAuth flow the owner approves), not just the bearer tokens the prototype uses.
- **OpenAI's Secure MCP Tunnel** is the same outbound pattern as our relay, but only for OpenAI. It is a useful second path for ChatGPT if the OAuth front slips, not a replacement.
- **Local CLI agents don't need the relay at all.** Claude Code and Codex run on the Mac; their file access is solved by confining them to the task worktree (1.4) and pointing them at the hub on localhost.

## The prototype (what was built and proven)

- **Hub file broker** (`packages/hub/src/files/`): folder grants (per room, per agent, read and write separate; refused for `/`, home itself, credential folders and the hub's data dir); path resolution that real-paths every component and refuses traversal, absolute paths, NUL and control characters, invisible Unicode, and any symlink that lands outside the grant; writes as SHA-pinned diff proposals that apply atomically only after owner approval, with conflict detection if the file changed meanwhile; `.git` writes refused on the resolved path; diffs too large to show are refused rather than summarised; every operation audited.
- **MCP tools**: `list_granted_folders`, `list_files`, `read_file`, `propose_file_write`, `file_write_status`. Owner REST: `/folder-grants`, `/write-proposals`.
- **Relay** (`packages/relay/`) and **hub tunnel** (`packages/hub/src/relay/tunnel.ts`): the hub dials out over WebSocket; cloud clients call `/h/<hub-id>/mcp`; only `/mcp` crosses (allowlisted at both ends); streamed responses (SSE) pass through; the hub still authenticates every MCP call itself. Enabled with `AGENT_ROOM_RELAY_URL`, `AGENT_ROOM_RELAY_HUB_ID`, `AGENT_ROOM_RELAY_SECRET`.
- **Evidence**: test `I1: an agent that reaches the hub only through the relay reads a granted file and gets a write applied after the owner approves` (packages/hub/test/relay.test.ts) is the acceptance sentence run literally. Supporting: 28 file-broker tests (`files.test.ts`), 12 relay tests, 5 hub relay end-to-end tests.

Reviewer: separate agent, read-only, given the code and the checklist, not this memo. Different model from the builders, **same vendor**: a cross-vendor review (Codex) is still owed before 1.1 merges, per the plan's reviewer rule.

| Symlinks | PASS after fixes (an inner symlink into `.git` bypassed the `.git` guard; fixed, regression test added) |
| Access outside granted folders | PASS |

| Cloud agents reach files only through the hub | PASS |
| Outbound-only relay, no inbound ports | PASS; end-to-end encryption NOT done (1.2) |

**Verdict: acceptable as a spike to support D1. Not ready for production (1.1).** Fixed during the spike: blind approvals of diffs over 5,000 lines (high), the `.git` guard bypass (medium), a malformed hub frame crashing the relay (medium), deceptive Unicode in file names, `/health` leaking hub presence through the relay, missing audit entries.

## What 1.1 and 1.2 must fix

1. **Approval UI shows the full diff.** The 8,000-character card is a preview; the owner decides on the full stored diff (`GET /write-proposals`). Neither app renders it yet.
2. **End-to-end encryption on the relay (1.2).** Today TLS ends at the relay, so the relay operator could read MCP traffic. Options: hub-terminated TLS through the tunnel, or an encrypted envelope between the vendor and the hub; at minimum wss-only and refusing plaintext to non-loopback relays.
3. **OAuth front and token hygiene.** Per-agent, per-room, expiring MCP tokens; hashed at rest; rotation; rate limits at the relay and the hub.
4. **Wider ungrantable set.** Dot-folders under home (`~/.claude`, `~/.codex`, `~/.config`, ...) and `~/Library`, unless the owner explicitly overrides.
5. **Write-only grants** shouldn't reveal whether a file exists or matches a guess.
6. **Room scoping for MCP apps.** Tokens from `POST /mcp-tokens` carry no room, so room-scoped grants only reach orchestrator-issued grants today.
7. **Relay robustness at scale.** Rate limits, backpressure for slow clients, streaming uploads, and hub routing outside process memory before running more than one relay instance.
8. **Check-to-use window.** Apply-time checks are real-path based with `O_NOFOLLOW`, but not `openat`-anchored; a local process racing a symlink swap in that window could redirect a write. Acceptable for a single-user Mac; revisit for 1.1.

## K5: where the relay prototype runs

**Proposed: Fly.io, one Machine in Chicago (`ord`) or Dallas (`dfw`), auto-stop off, shared-cpu-1x 512 MB, about $4 a month list price; TLS via `fly certs add`.** Before relying on it, soak-test a 2-minute SSE stream and a silent 1-hour WebSocket through Fly's proxy (Fly documents no WebSocket idle limit either way). **Fallback: Railway** (documents WebSockets as exempt from idle limits, with Serverless off). Rejected for this shape: Render Free (spins down after 15 minutes), Cloud Run (60-minute socket cap, about $43 a month always-on), Cloudflare Durable Objects (best at scale, but a rewrite). At scale the hub registry has to move out of process (one Durable Object per hub, or Redis) before running more than one relay instance.
