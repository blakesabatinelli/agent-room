# 1.1 Local file access: security checklist

For the independent reviewer. Each line says what must hold, where it is enforced, and the test that proves it.
Tests are in `packages/hub/test/fileaccess.test.ts` (new in 1.1), `packages/hub/test/fileaccess-hardening.test.ts` (the fixes after the independent review; each of its tests fails on the code as it was before), `packages/hub/test/fileaccess-round2.test.ts` (the second independent review, see "Round 2 review" below; same rule) and `packages/hub/test/files.test.ts` (the 0.3 broker tests, kept green).
Run: `cd packages/hub && npx tsx --test --test-timeout=180000 test/fileaccess.test.ts test/fileaccess-hardening.test.ts test/fileaccess-round2.test.ts test/files.test.ts test/worktree.test.ts`.

How to read the evidence: "Test" is what runs in CI on Linux with the real `git` binary and fake agents. "Not proven here" says what that test cannot show. The last section lists what has to be checked on a real Mac.

Threat model: an agent (local CLI, command adapter, or an MCP app on another machine or in the cloud) is trusted to do its job and not trusted with the rest of the disk. The owner is trusted. A paired phone is the owner. Anything that arrives through Tailscale Funnel is anonymous until it presents a key.

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| B1 | A link inside a grant that points outside it is refused for list and read, as a file and as a folder component | `resolveInGrant` (realpath of the longest existing ancestor, then re-check) | files: "traversal, absolute paths and symlink escapes (file and directory component) are denied and audited" |
| B2 | A write never follows a link: the final component is opened with `O_NOFOLLOW`, writes to a link are refused | `broker.writeGuard`, `readFile`, `atomicWrite` | files: "writes to symlinks, into .git, ..."; "a symlink planted after proposing cannot redirect the approved write outside" |

| C9 | An agent cannot make the hub run what it wrote into a repository's config, hooks or attributes. That also neutralises `filter.*`, `merge.*` and `diff.*` drivers, which have no name to override from the command line; (c) in a task worktree git is pointed at its git dirs directly (`GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`) and the worktree admin folder's `commondir` is put back, so an agent cannot redirect the hub to a repository of its own; (d) the `.git` file in the work folder is restored as before. Round 2: the hub's own `_integration` worktree is bound the same way (H1), the config is never re-snapshotted after `git worktree add` (M2), and every restore of a worktree's git files is audited as `worktree.tampered`. `ControlGit` (the control folder's history) gets layer (a) | `files/gitSafe.ts`, `worktree.ts` `git()`/`bind()`/`restorePointer`, `control/git.ts` | hardening: "1a: every hub git call carries the overrides ..."; "1a: with a poisoned config, plain git runs the command and the hardened flags do not ..." (control: the attack is real on this git); "1: an agent that edits the shared git config, hooks and attributes cannot make the hub run them (fsmonitor, filter, merge driver, diff, hooks) ..." (marker files; goes through a real merge); "1: an agent that rewrites its worktree's commondir ..."; fileaccess: "AC2: an agent that swaps its work folder's .git ...". **Not proven here:** see limits 1 and 2 |
| C10 | The owner's checked-out branch, working tree, `.git`, config, hooks, remotes and reflogs are never touched or seen by a goal on a granted repo. The hub makes its OWN clone of the owner's repo in its data folder (`init --template=` + `fetch` of the checked-out head, or of `agent-room/<goal>` if the owner already has it; over the file protocol, no tags, submodules, remote, hooks or reflog; `FETCH_HEAD` removed), cuts task worktrees from the clone, merges accepted work on `agent-room/<goal>` there, and pushes that one branch to the owner's repo with `git push <owner path> <recorded commit id>:refs/heads/agent-room/<goal>` (never forced, receiving-side hooks off, `receive.denyCurrentBranch=refuse` forced on the receiving side; round 2 M5 and L6). A branch the owner moved or has checked out is refused by git; that is reported to the owner and the work waits in the clone (pushed again after the next task; at cleanup a clone that still cannot push is moved to `<data>/unpushed/<goal>` and audited as `goal.source.unpushed`) | `worktree.ts` `makeClone`, `ensureSource`, `pushToOwner`, `removeSource`; `files/goalSource.ts` `afterAccept` | fileaccess: "AC2/AC4: a goal on a granted git repo lands accepted work of two tasks on agent-room/<goal> ..." (unchanged and green); hardening: "3: a granted repo is cloned into the hub's data folder; the agent's worktree shares the clone's .git, which has no trace of the owner's repo; accepted work is pushed back" (token in remote URL, owner hooks and owner `core.fsmonitor` never reach the clone or run; owner config byte-identical); "3: when the owner has the goal branch checked out the push is refused and reported ..." |
| C11 | A read-only grant writes nothing back, ever (no proposal, no branch) | `worktree.ts` `accept` (`withheld`), `goalSource.ts` | fileaccess: "a read-only grant: tasks read the folder but nothing is ever written back" |
| C12 | A goal on a granted folder keeps its authority: the grant is re-checked (`usable()`: exists, readable, open to every agent, this room) every time the goal's folder is resolved, before each task starts and at the moment of merging. A grant that fails (removed, narrowed to one agent, moved to another room, made unreadable) is revoked for the goal: no task starts, nothing is merged or written back, the goal is stopped, the owner is told once (`goal.source.revoked`) | `goalSource.ts` `ref`/`lost`/`firstLoss`, `orchestrator.ts` `runTask` hook and `stopForLostFolder` | hardening: "5: GoalSources.ref re-checks the grant ..."; "5: narrowing the grant while a goal waits for plan approval stops the goal: no task runs, nothing is written, the owner is told once" |

## D. Writes and approvals

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| D1 | Nothing is written until the owner approves; a rejection, an expiry or a hub restart leaves the file alone | `broker.finish`, `expireStale` | files: "propose, approve ...", "propose, reject ...", "an approval that expires ...", "proposals are capped and a restart expires the ones still waiting" |
| D2 | Auto-approve settings never skip a file write | `broker.register` (own approval, no `auto`) | files: "applying keeps the file's permissions; an auto-approve setting does not skip the owner" |
| D3 | A write the file changed under (edited, created or deleted meanwhile) is a conflict and writes nothing | `broker.finish` (SHA pinned at proposal time) | files: "file edited by someone else before approval: conflict ..."; fileaccess: "a non-git proposal conflicts, and writes nothing, when the owner changed the file meanwhile" |
| D4 | The owner can read what they approve: an over-long diff on the approval card is cut with a loud warning, the whole diff is on `GET /write-proposals/:id`, and a change too big to diff is refused | `broker.register`, `server.ts` | fileaccess: "d: /write-proposals/:id returns the whole stored diff ..."; files: "H1: a change too big to diff is DENIED ..." |
| D5 | A task's write-back to a non-git folder is ONE approval listing every file with its full diff, and applies all files or none | `broker.proposeTask`, `finish` (checks all, then writes, rolls back on error) | fileaccess: "AC4: a goal on a granted non-git folder ..." |
| D6 | Removing a grant, or taking away its write bit, settles waiting writes at once; switching the filesystem tool off stops them at apply time | `broker.updateGrant/removeGrant/cancelPending`, `finish` | files: "removing the grant, or switching the tool off, while a write waits stops it" |
| D8 | Narrowing a grant to another agent or room settles the waiting writes of the old audience at once (`updateGrant`), and the apply step checks again that `grantsFor(proposing agent, room)` still includes the grant, so a change that bypassed `updateGrant` is caught too | `broker.updateGrant`, `broker.finish`, `broker.covers` | hardening: "4: narrowing a grant to another agent or room settles the writes already waiting; and the apply step checks again even if the narrowing bypassed updateGrant" |
| D9 | One agent cannot fill the owner's approval queue: 20 waiting writes per agent, 50 in all (a task's write-back counts too) | `broker.proposeWrite`, `proposeTask` (`MAX_PENDING_PER_AGENT`) | hardening: "8: one agent gets 20 waiting writes; other agents can still propose; the hub-wide cap stays 50"; files: "proposals are capped and a restart expires the ones still waiting" |
| D7 | Binary and invalid UTF-8 are refused the same way for read and write, with the same words; a read cut inside a character is still text | `files/text.ts`, `broker.read/proposeWrite` | fileaccess: "e: read and write refuse binary and invalid UTF-8 the same way" |

## Known limits (accepted, owner informed)

Read these as the boundary of what the evidence above shows.

1. **An agent with no OS sandbox runs as the owner.** A command adapter, or Claude Code with `bashSandbox: false`, can write any file the owner can write: the hub's database, other worktrees, even the owner's repository by absolute path. Layers (a) to (d) in C9 stop the specific route "make the hub run my code through git", not the agent itself. Round 2 closes the specific route through the hub's `_integration` worktree (H1) and through agent-writable refs (M5). The OS sandbox (Claude Code's Bash sandbox, Codex's workspace-write) is what confines such an agent; a command adapter has none and must be treated as trusted code. Claude Code's own sandbox additionally denies writes to `config` and `hooks` inside a linked worktree's shared `.git` (sandboxing docs, "Git worktrees"), which closes the route for sandboxed Bash.
2. **The config guard is not a lock.** It puts the config back before each hub git call. An agent process left running in the background could change it between the restore and the git call (a race), and only drivers that can be named are covered by layer (a) alone (`filter`, `merge`, `diff` drivers rely on the restore). A repository the hub made before this fix has no snapshot, so its config is trusted the first time it is used (the same for a goal's `tip` and integration pointers made before round 2: recorded once, on first use). Round 2: after `git worktree add` the snapshot is no longer retaken; only `extensions.worktreeConfig` and `core.repositoryformatversion` may differ, everything else is put back. The ids the hub records (a task's commit, the goal branch's tip) are read from refs right after the hub wrote them, so a process that moves a ref in that instant still wins; the window is milliseconds and the result is caught at the push (it refuses a branch that no longer holds the recorded id). Per-worktree files an agent can write (`HEAD`, `index` in `.git/worktrees/<name>`) are the agent's own state and are not guarded.
3. **Bash read scope.** With the allow-list in C5a a sandboxed Bash command reads: its worktree, its repository's git dir, toolchain folders under home, and everything OUTSIDE the home folder and the data folder (for example `/tmp`, `/Volumes`, other users' folders, `/Library`). Claude Code's `permissions.blockReadsOutsideWorkingDirectories` (set by the hub, Claude Code 2.1.257 or later per its docs) is documented to also block sandboxed commands from the home folder and mounted volumes; on an older Claude Code that part is not enforced. If a Claude Code version ignores `allowRead`, the worktree itself would be unreadable (the run fails; it does not fall open). The agent can read the committed history of its own repository, which for a granted repo is the whole history of the owner's checked-out branch (secrets committed there included): the folder was granted to the goal. Remote URLs, tokens, hooks and other branches are not in the clone.
4. **Codex's read access outside the worktree is not confined** by its sandbox flags (writes are, including `/tmp` and `$TMPDIR`). Needs a real Codex run on a Mac to confirm.
5. **Claude Code's Bash sandbox is OS-level (Seatbelt on macOS) and was verified live only on Linux.** `agent.settings.bashSandbox: false` turns it off per agent. Home-folder denial may break tools that read dot-files not on the toolchain list; add them in `agent.settings.sandboxReadAllow`.
6. `--setting-sources ""` means the owner's own Claude Code settings do not apply to hub runs. Round 2: planner, judge and draft calls (`jsonOnly`) also run with it, with `--strict-mcp-config` and no tools, so the owner's own MCP servers are not loaded in them either.
6a. **File tools depend on the hub's approval prompt (round 2, M3).** Claude Code is given no allow rule for them, so with no `--permission-prompt-tool` (a run without the hub's MCP server) every file tool call is refused: it fails closed, it does not fall open. Each call is one MCP round trip to the local hub (a realpath and a few `lstat` calls), with no card for work inside the task folder.
6b. **Home-folder read allowances are by folder name.** A toolchain installed under a name that is not in `TOOLCHAIN_HOME_DIRS` is not readable from Bash until the owner adds it to `agent.settings.sandboxReadAllow`. `~/.gitconfig` is still re-opened whole (it can hold `url.<token>@...insteadOf` rewrites if the owner put a token there).
7. **Granted-git specifics.** The clone holds tracked content of the checked-out head only: not untracked or uncommitted files, not submodule contents, and Git LFS files appear as pointer files (the hub does not run `filter.lfs`). The owner's server-side hooks (`pre-receive`, `update`, `post-receive`) do not run on the hub's push, by design. If the owner has `agent-room/<goal>` checked out, or moved it, the push is refused and the work waits in the clone (and is kept under `<data>/unpushed/<goal>` if it still cannot be pushed when the goal is cleaned up).
8. **Hard links** are refused inside worktrees, copies and broker reads. A hard link elsewhere on the disk is not looked for. Skipping costs fidelity: a granted folder that legitimately holds hard-linked files gets those files left out of the private copy (reported in the audit log as `goal.source.skipped`).
9. **The write-proposal queue is capped per agent (20)**, so an agent whose many tasks each produce a non-git write-back can have later ones refused ("could not be prepared"); the accepted work stays in the private copy until the goal ends.
10. Pending proposals live in memory: a hub restart expires them. Accepted work of a non-git goal that is waiting for approval is lost on restart.
11. A hub-forced grant of a protected folder is the owner's call; the reason is audited.
12. Old copies of the database (backups, snapshots) can still hold legacy plaintext MCP keys; `VACUUM` only cleans the live file.
