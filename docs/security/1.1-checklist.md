# 1.1 Local file access: security checklist

For the independent reviewer. Each line says what must hold, where it is enforced, and the test that proves it.
Tests are in `packages/hub/test/fileaccess.test.ts` (new in 1.1) and `packages/hub/test/files.test.ts` (the 0.3 broker tests, kept green).
Run: `cd packages/hub && npx tsx --test test/fileaccess.test.ts test/files.test.ts`.

Threat model: an agent (local CLI, command adapter, or an MCP app on another machine or in the cloud) is trusted to do its job and not trusted with the rest of the disk. The owner is trusted. A paired phone is the owner. Anything that arrives through Tailscale Funnel is anonymous until it presents a key.

## A. Path traversal

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| A1 | `..`, absolute paths, NUL, empty, over-long and encoded-slash paths never leave the granted folder, for list, read and write | `files/paths.ts` `resolveInGrant`, `assertPlainPath` | files: "resolveInGrant: traversal, absolute, NUL, empty, long and symlink escapes are refused"; "traversal, absolute paths and symlink escapes ... are denied and audited" |
| A2 | Control characters, direction-changing characters and a trailing slash in a path are refused | `broker.proposeWrite`, `assertPlainPath` | files: "L1: names with invisible or direction-changing characters, or a trailing slash, are refused" |
| A3 | Audited paths are never cut short, so the log shows the real path | `broker.q`, `MAX_REL_PATH` | files: "I3: audited paths are not cut short below the 1,024 character path limit" |
| A4 | `.git` is never read, listed or written through a grant (it can hold credentials and hooks), in any spelling or through a linked folder | `files/paths.ts` `touchesGit`, `broker.list/read/writeGuard` | files: "writes to symlinks, into .git, ..."; "M1: a symlinked folder that points at .git cannot be used to write into .git" |

## B. Symlinks

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| B1 | A link inside a grant that points outside it is refused for list and read, as a file and as a folder component | `resolveInGrant` (realpath of the longest existing ancestor, then re-check) | files: "traversal, absolute paths and symlink escapes (file and directory component) are denied and audited" |
| B2 | A write never follows a link: the final component is opened with `O_NOFOLLOW`, writes to a link are refused | `broker.writeGuard`, `readFile`, `atomicWrite` | files: "writes to symlinks, into .git, ..."; "a symlink planted after proposing cannot redirect the approved write outside" |
| B3 | The path is checked again when the owner approves, so a link planted while the proposal waited cannot redirect it | `broker.finish` | files: "a symlink planted after proposing cannot redirect the approved write outside" |
| B4 | The owner approves the real location, not the spelling the agent used | `broker.proposeWrite` (`shown`) | files: "M1: the owner sees the resolved path, not the symlinked spelling the agent used" |
| B5 | Copying a granted folder into a private base never follows links out (links are skipped and counted) | `worktree.ts` `copyGrantedTree` | fileaccess: "AC4: a goal on a granted non-git folder writes nothing until the owner approves ..." (folder holds only plain files); `copyGrantedTree` skips every non-regular entry by construction |

## C. Access outside granted folders

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| C1 | No grant, no access. The agent's filesystem switch, the grant's read/write bits, its agent and its room all apply, and a room-scoped grant is invisible from another room | `broker.authorize`, `grantsFor` | files: "read without a grant is denied ...", "a read-only grant cannot be written to", "room-scoped grants are invisible from other rooms ..." |
| C2 | A key pinned to a room only sees that room's grants, and cannot name another room in any tool argument | `mcp/server.ts` `scoped()`; `mcp/tokens.ts` | fileaccess: "c: a key pinned to a room only sees that room's folder grants and cannot name another room" |
| C3 | Ungrantable folders: `/`, the home folder and anything containing it, never. Every dot-folder under home, `~/Library`, `/System`, `/Library`, `/private`, `/etc`, `/usr`, `/bin`, `/sbin`, `/Applications`, `/var`, the hub data folder and the control folder's `.git` only with `force` and a written reason | `files/paths.ts` `inspectGrantRoot`, `broker.addGrant` | fileaccess: "ungrantable folders are refused; protected ones are allowed only with force and a reason, and that is audited"; the grant API test for the 400 body (`code`, `canForce`) |
| C4 | A forced grant records the owner's reason on the grant and in the audit log (`grant.override`) | `broker.addGrant` | fileaccess: same test as C3 |
| C5 | A local agent is confined to its task worktree: cwd, one `--add-dir`, no settings files, deny rules for credential folders and the hub's data, scoped allow rules, Bash sandbox with `failIfUnavailable` | `files/confine.ts`, `adapters/claudeCode.ts` | fileaccess: "AC2: Claude Code argv confines the run to its worktree ..." |
| C6 | Codex gets `-C <worktree>`, `workspace-write`, no extra writable roots, `/tmp` not writable; planning calls are read-only | `adapters/codex.ts` `codexBaseArgs` | fileaccess: "AC2: Codex runs with -C <worktree>, workspace-write and no extra writable roots ..." |
| C7 | A command adapter gets the worktree as its cwd and nothing else | `adapters/command.ts` | fileaccess: "AC2: a command adapter gets the worktree as its cwd ..." |
| C8 | Defense in depth: a file tool aimed outside the worktree is refused by the hub's `approval_prompt`, whatever the owner's approval settings, including through a link and through `~` | `files/confine.ts` `checkFileToolRequest`, `mcp/server.ts` | fileaccess: "AC2: the hub refuses a file tool aimed outside the task folder ..." |
| C9 | An agent cannot make the hub run its own git config: the work folder's `.git` pointer is restored before the hub runs git there | `worktree.ts` `restorePointer` | fileaccess: "AC2: an agent that swaps its work folder's .git for a repository of its own ..." |
| C10 | The owner's checked-out branch and working tree are never touched by a goal on a granted repo; accepted work lands on `agent-room/<goal>` | `worktree.ts` (hub-owned integration worktree), `files/goalSource.ts` | fileaccess: "AC2/AC4: a goal on a granted git repo lands accepted work of two tasks on agent-room/<goal> ..." |
| C11 | A read-only grant writes nothing back, ever (no proposal, no branch) | `worktree.ts` `accept` (`withheld`), `goalSource.ts` | fileaccess: "a read-only grant: tasks read the folder but nothing is ever written back" |

## D. Writes and approvals

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| D1 | Nothing is written until the owner approves; a rejection, an expiry or a hub restart leaves the file alone | `broker.finish`, `expireStale` | files: "propose, approve ...", "propose, reject ...", "an approval that expires ...", "proposals are capped and a restart expires the ones still waiting" |
| D2 | Auto-approve settings never skip a file write | `broker.register` (own approval, no `auto`) | files: "applying keeps the file's permissions; an auto-approve setting does not skip the owner" |
| D3 | A write the file changed under (edited, created or deleted meanwhile) is a conflict and writes nothing | `broker.finish` (SHA pinned at proposal time) | files: "file edited by someone else before approval: conflict ..."; fileaccess: "a non-git proposal conflicts, and writes nothing, when the owner changed the file meanwhile" |
| D4 | The owner can read what they approve: an over-long diff on the approval card is cut with a loud warning, the whole diff is on `GET /write-proposals/:id`, and a change too big to diff is refused | `broker.register`, `server.ts` | fileaccess: "d: /write-proposals/:id returns the whole stored diff ..."; files: "H1: a change too big to diff is DENIED ..." |
| D5 | A task's write-back to a non-git folder is ONE approval listing every file with its full diff, and applies all files or none | `broker.proposeTask`, `finish` (checks all, then writes, rolls back on error) | fileaccess: "AC4: a goal on a granted non-git folder ..." |
| D6 | Removing a grant, or taking away its write bit, settles waiting writes at once; switching the filesystem tool off stops them at apply time | `broker.updateGrant/removeGrant/cancelPending`, `finish` | files: "removing the grant, or switching the tool off, while a write waits stops it" |
| D7 | Binary and invalid UTF-8 are refused the same way for read and write, with the same words; a read cut inside a character is still text | `files/text.ts`, `broker.read/proposeWrite` | fileaccess: "e: read and write refuse binary and invalid UTF-8 the same way" |

## E. Write-only grants (no oracle)

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| E1 | On a write-only grant an agent cannot learn whether a path exists, what kind of thing it is (file, folder, link, binary, invalid text), or whether its content is identical: every such proposal is accepted and looks the same, and the owner sees why it cannot be applied | `broker.proposeWrite` (`unappliable`), `proposalFor` | fileaccess: "a write-only grant never reveals whether a path exists, what it is, or whether content is identical" |
| E2 | After the owner decides, "owner said no", "cannot be applied" and "file changed" read the same to the agent | `broker.proposalFor` | same test |
| E3 | Read and list on a write-only grant answer the same whatever is there; the diff shown to the agent is withheld | `authorize`, `proposalFor` | same test; files: "a write-only grant never shows the agent the existing file through the diff" |

## F. Remote access (agents on other devices or in the cloud)

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| F1 | Through Funnel (or any proxy) only `POST /mcp` and its 405 `GET` answer; every other route is 404, even with a paired device's token. Includes `/goals/:id/files`, `/goals/:id/reveal` and `/documents` | `api/server.ts` `onRequest` hook | fileaccess: "AC3: a proxied request to /goals/:id/files, /goals/:id/reveal and /documents is refused ..."; "AC3: no route but /mcp answers a proxied request ... (inventory of every registered route)" |
| F2 | Every route except `/health`, `/pair`, `/pair/local`, `/mcp` and the phone page needs a paired device | same hook | same inventory test |
| F3 | No route returns file content to the app except through the file broker's own tools; the three listed above return names from the hub's own folders, behind a paired device | review of `api/server.ts` | inventory test (F1) plus the list in the "Audit of routes" section below |
| F4 | A cloud agent reaches files only through MCP tools, with its key, and each call is audited as that agent | `mcp/server.ts`, `mcp.remote` audit | fileaccess: "AC3/AC5: a cloud agent reaches files only through the MCP tools, and each call is audited as that agent" |

## G. MCP keys

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| G1 | Keys are stored as SHA-256 hashes; the database file, the key list and the audit log never hold a key | `mcp/tokens.ts` | fileaccess: "c: MCP keys are hashed at rest ..." |
| G2 | Legacy plaintext keys are migrated on start, keep working, and are wiped from the old place | `McpTokens.migrate` | fileaccess: "c: legacy plaintext keys are migrated to hashes on start and keep working" |
| G3 | Keys may expire (enforced, audited as `mcp.token.expired` without the key), rotate (old key dies at once) and be revoked | `McpTokens`, `server.ts` `/mcp` | fileaccess: "c: expiry is enforced, an expired key is audited without the key, rotation retires the old key, revoke ends it" |
| G4 | Failed key guesses through Funnel are rate limited | `remote/guard.ts` `AuthLimiter` (1.2) | remote.test.ts (1.2) |
| G5 | A key is shown once. After a hub restart the Connect screen cannot show it (`tokenHidden`), only rotate it | `server.ts` `connectionFor` | api: "MCP keys for Hermes and Muse survive a hub restart and only change on request" |

## H. Audit (every file operation, grant change, key change)

| # | Must hold | Test |
|---|---|---|
| H1 | List, read, denial, proposal, apply, reject, conflict, expire, grant add, change, remove, override, token create, rotate, revoke, expire: one entry each (one per file for a task write-back), with actor and path, and never file contents or keys | fileaccess: "AC5: every file operation, grant change and key change is audited with who and what, never with contents or keys" |
| H2 | Remote `/mcp` calls are audited with the agent and the key id, never the key | fileaccess: "AC3/AC5: a cloud agent reaches files only through the MCP tools ..." |

Audit action names: `file.list`, `file.read`, `file.denied`, `file.write.proposed`, `file.write.applied`, `file.write.rejected`, `file.write.conflict`, `file.write.rollback_failed`, `file.writeback.none`, `file.writeback.withheld`, `file.grants.listed`, `file.write.status`, `grant.added`, `grant.changed`, `grant.removed`, `grant.override`, `goal.source.set`, `goal.source.merged`, `mcp.token.created`, `mcp.token.rotated`, `mcp.token.revoked`, `mcp.token.migrated`, `mcp.token.expired`, `mcp.remote`.

## Audit of routes that return file content or file names

| Route | Returns | Reachable from Funnel | Needs paired device |
|---|---|---|---|
| `GET /goals/:id/files` | names in the hub's own goal folder | no (404) | yes |
| `POST /goals/:id/reveal` | nothing (opens Finder on the Mac) | no (404) | yes |
| `GET /documents` | the Library index (titles, paths) | no (404) | yes |
| `GET /write-proposals`, `GET /write-proposals/:id` | proposals and diffs, to the owner | no (404) | yes |
| `GET /folder-grants*` | grants, to the owner | no (404) | yes |
| `POST /mcp` tools `list_files`, `read_file`, `propose_file_write`, `file_write_status`, `list_granted_folders` | file content and names inside grants | yes, with a valid key | key |

## Known limits (accepted, owner informed)

- Codex's read access outside the worktree is not confined by its sandbox flags (writes are). Needs a real Codex run on a Mac to confirm.
- The Bash sandbox of Claude Code is OS-level (Seatbelt on macOS) and was verified live only on Linux; check it on a real Mac. `agent.settings.bashSandbox: false` turns it off per agent.
- `--setting-sources ""` means the owner's own Claude Code settings do not apply to hub runs.
- Pending proposals live in memory: a hub restart expires them. Accepted work of a non-git goal that is waiting for approval is lost on restart.
- A hub-forced grant of a protected folder is the owner's call; the reason is audited.
