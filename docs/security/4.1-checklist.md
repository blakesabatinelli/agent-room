# 4.1 Two-key actions: security checklist

For the independent reviewer. Each line says what must hold, where it is enforced, and the test that proves it.
All tests are in `packages/hub/test/twokey.test.ts`. Run: `cd packages/hub && npx tsx --test test/twokey.test.ts`.

What it is: sending email, writing to a CRM and deleting anything need two keys. The agent asking is key A. The hub asks one agent from a different model family to draft the same action on its own (key B). Matching drafts go on to the usual approval rules. Anything else is the owner's decision, on one card showing both drafts.

Threat model: an agent can be wrong, confused or manipulated by content it read, and may draft a bad action with full confidence. A second vendor's model, given the task but not the first draft, is unlikely to make the same mistake in the same way. The owner is trusted. This is not a defence against two vendors agreeing on a wrong action.

Code: `packages/hub/src/twokey/` (`classify.ts`, `shell.ts`, `draft.ts`, `text.ts`, `match.ts`, `pick.ts`, `prompt.ts`, `service.ts`, `records.ts`, `routes.ts`). Choke points: `orchestrator.requestApproval` (calls `twoKey.gate`), `files/broker.ts` `register` (delete proposals call `twoKey.checkDeletes`).

## AC1. Email send, CRM writes and deletes require independent drafts from two vendors

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| 1.1 | Classification is table-driven: email send/reply/forward (gmail, outlook, any matching MCP name), CRM create/update/upsert/delete (salesforce and other CRM connectors by name), every delete (file, CRM, email thread), shell deletes. | 1.2 | Shell deletes are two-key: `rm`, `rmdir`, `unlink`, `git clean`, `find -delete/-exec rm`, `rsync --delete`, wrappers (`sudo`, `env`, `xargs`, `timeout`), `sh -c`, chains and pipes. ## AC2. The action runs only if the drafts match; otherwise the user decides

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| 2.1 | Independence: the second agent gets the objective, criteria, relevant inputs and conversation, and never the first draft: not the recipients, subject, body, tool input or the first agent's own words about it | `prompt.ts` `twoKeyPrompt`, `service.ts` `brief` (redacts the first draft's text from the conversation) | "AC2: the second agent never sees the first draft, nor the words the first agent used to ask; it does get the work" (inspects `MockAdapter.calls`) |
| 2.2 | Exact match on critical fields: email recipients (to, cc, bcc; lowercased, sorted), CRM object, operation, record and every field value (normalised), delete targets (paths resolved) | `match.ts` `compareDrafts` | "matching: the same email in other words matches; recipients, numbers, ... do not"; "matching: a CRM write is exact on object, operation, record and every field; ..."; "matching: delete targets are exact once paths are resolved; ..." |
| 2.3 | Free text matches only if the token similarity is at or above the threshold (default 0.85) AND no number, date, time, amount, link or name is in one and not the other. Sign-offs are ignored, but anything after a sign-off that is not a name or title (a link, a number, a P.S.) is compared | `text.ts` `similarity`, `entitiesOf`, `stripSignoff` | "matching: the same email in other words matches; ... do not"; "matching: entities are found in their many spellings"; "a practice run never reaches the second key; ...; a stricter threshold, changes the check" |
| 2.4 | A match goes through the normal approval rules. It never bypasses an owner "always ask" rule. It replaces the owner only where policy already allows auto-approval | `orchestrator.requestApproval` (the gate calls back into `requestApproval` with `twoKeyDone`) | "AC1: an email send gets an independent draft ... (auto-approval stands in for the owner)"; "AC1: a match never bypasses an owner rule that says always ask ..." |
| 2.5 | A mismatch (recipients, an extra number, wording too different), "no action", or an unreadable reply makes exactly one owner card with both drafts. Nothing runs until the owner picks | `service.ts` `run` (one `approvals.request` with `twoKey` card) | "AC2: recipients that differ, an extra number in the body, or 'no action' make exactly one owner card with both drafts; nothing runs until the owner picks" |
| 2.6 | The card options are run A, run B, run neither (B only when B drafted something). A plain Reject is neither. A plain Approve with no pick is refused (400). No decision (expired) runs nothing | `api/server.ts` POST `/approvals/:id`, `service.ts` | "AC2: the owner picking draft A runs A only; picking B hands the agent B instead; picking neither runs nothing"; "AC2: the card is a disagreement for the attention gate ..." | 2.7 | Picking A runs A only. Picking B hands the agent draft B instead (`request_approval` says so, `approval_prompt` replaces the input or issues a one-use permit for the exact draft). An ACP agent cannot be handed B, so a B pick is denied | `mcp/server.ts`, `service.ts` `permit`, `orchestrator.ts` ACP approve callback | "AC2: the owner picking draft A runs A only; ..."; "AC2 over MCP and HTTP: ..." |
| 2.8 | File deletes: a match leaves the owner's usual approval (with a note) and the file goes only when the owner approves. A mismatch is one card (A deletes what was asked, B deletes the other agent's list, neither deletes nothing). With no second family it is the owner's card | `files/broker.ts` `twoKeyDeletes`, `applyDeleteDraft` | "AC1: a file delete goes through the same check; ..."; "AC2: a file delete the drafts disagree on is one card; ..."; "AC2: a file delete with no second family is the owner's decision on a card (never one key); ..." |
| 2.9 | A request that deletes more than it lists (`git clean`, `find -delete`) never matches a list | `match.ts` `compareDelete` (`unparsed`) | "matching: delete targets are exact once paths are resolved; a request that deletes more than it lists never matches" |
| 2.10 | A disagreement goes through the attention gate as a `disagreement` (an interruption, `blocking` so it is always pushed) | `attention/gate.ts` `onEvent` | "AC2: the card is a disagreement for the attention gate (counted as an interruption, blocking so it is always pushed)"; "AC2: recipients that differ, ..." (checks the push) |

## Known limits (stated, not hidden)

- The first draft is read from the tool input by key names (to, cc, subject, body, sobject, id, fields...). An unfamiliar input shape gives no draft, and then the owner decides (verdict `mismatch`/`unavailable`, never a pass). A free-text `request_approval` detail that is not JSON or `To:`/`Subject:` lines is unreadable the same way.
- Names are found by capitalisation. Number words ("three") are not entities. A differing word the heuristic does not see passes if the similarity is high enough.
- The shell parser is conservative but not complete: output redirection (`> file`) that truncates, and a script file that deletes, are not caught. This is the same as the existing approval rules for shell.
- The second agent runs JSON-only with no tools, so it cannot look anything up; it works from the task context it is given.
- Two vendors agreeing on a wrong action is not detected.
- The ACP adapter cannot be handed draft B. A B pick is denied for it.

## Verify on a real Mac

- With two real agents of different vendors (for example Claude Code and Codex), ask for an email send and read both drafts on the card.
- The card in the Mac app and the web app with long bodies, and in dark mode.
