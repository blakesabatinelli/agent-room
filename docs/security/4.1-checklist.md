# 4.1 Two-key actions: security checklist

For the independent reviewer. Each line says what must hold, where it is enforced, and the test that proves it.
Tests are in `packages/hub/test/twokey.test.ts` (and, for the policy findings below, `packages/hub/test/policy.test.ts`). Run: `cd packages/hub && npx tsx --test test/twokey.test.ts test/policy.test.ts`.

What it is: sending email, writing to a CRM and deleting anything need two keys. The agent asking is key A. The hub asks one agent from a different model family to draft the same action on its own (key B). Matching drafts go on to the usual approval rules. Anything else is the owner's decision, on one card showing both drafts.

Threat model: an agent can be wrong, confused or manipulated by content it read, and may draft a bad action with full confidence. A second vendor's model, given the task but not the first draft, is unlikely to make the same mistake in the same way. The owner is trusted. This is not a defence against two vendors agreeing on a wrong action.

Code: `packages/hub/src/twokey/` (`classify.ts`, `shell.ts`, `draft.ts`, `text.ts`, `match.ts`, `pick.ts`, `prompt.ts`, `service.ts`, `records.ts`, `routes.ts`). Choke points: `orchestrator.requestApproval` (calls `twoKey.gate`), `files/broker.ts` `register` (delete proposals call `twoKey.checkDeletes`).

## AC1. Email send, CRM writes and deletes require independent drafts from two vendors

| # | Must hold | Enforced in | Test |

## AC2. The action runs only if the drafts match; otherwise the user decides

| # | Must hold | Enforced in | Test |
|---|---|---|---|
| 2.1 | Independence: the second agent gets the objective, criteria, relevant inputs and conversation, and never the first draft: not the recipients, subject, body, tool input or the first agent's own words about it | `prompt.ts` `twoKeyPrompt`, `service.ts` `brief` (redacts the first draft's text from the conversation) | "AC2: the second agent never sees the first draft, nor the words the first agent used to ask; it does get the work" (inspects `MockAdapter.calls`) |
| 2.2 | Exact match on critical fields: email recipients (to, cc, bcc; lowercased, sorted), CRM object, operation, record and every field value (normalised), delete targets (paths resolved) | `match.ts` `compareDrafts` | "matching: the same email in other words matches; recipients, numbers, ... do not"; "matching: a CRM write is exact on object, operation, record and every field; ..."; "matching: delete targets are exact once paths are resolved; ..." |
| 2.3 | Free text matches only if the token similarity is at or above the threshold (default 0.85) AND no number, date, time, amount, link or name is in one and not the other. Sign-offs are ignored, but anything after a sign-off that is not a name or title (a link, a number, a P.S.) is compared | `text.ts` `similarity`, `entitiesOf`, `stripSignoff` | "matching: the same email in other words matches; ... do not"; "matching: entities are found in their many spellings"; "a practice run never reaches the second key; ...; a stricter threshold, changes the check" |

## Independent review findings (4.1 and 4.2): what was fixed, and the test that proves it

Guiding rule: when the hub is unsure whether an action sends email, writes to a CRM or deletes, it is two-key and the owner decides. There is one classifier (`twokey/classify.ts` `isTwoKey`); the gate, the policy, the learner and the agent's auto-approval all call it.
Tests named below are in `packages/hub/test/twokey.test.ts` unless marked (policy), which means `packages/hub/test/policy.test.ts`.

| Id | Finding | Fix | Regression test |
|---|---|---|---|
| H1 | The connector id was matched by substring, so `pipedrive` became `drive` and its CRM writes were not two-key | `classify.ts` `toolIdOf` matches whole words; classification is always on the words of the tool and the action together | "H1: a tool is a hub tool only by whole words: `pipedrive` is not Google Drive, ..." |
| H2 | "Read only" was decided from the agent's own input words (`{type:"readonly", op:"update"}`) | Read-only comes from the tool's name only; a write verb in the input always makes the call two-key | "H2: whether a connector call only reads comes from its own name, never from words in its input ..." |

## Known limits (stated, not hidden)

- The first draft is read from the tool input by key names (to, cc, subject, body, sobject, id, fields...). An unfamiliar input shape gives no draft, and then the owner decides (verdict `mismatch`/`unavailable`, never a pass). A free-text `request_approval` detail that is not JSON or `To:`/`Subject:` lines is unreadable the same way.
- Names are found by capitalisation. Number words ("three") are not entities. A differing word the heuristic does not see passes if the similarity is high enough.
- The shell parser is conservative but not complete: a script file that deletes (`./cleanup.sh`) is not read, and neither are `git reset --hard` or `git checkout -- <file>` (they discard work but are not deletes). Everything it cannot read (an interpreter's code, a command from stdin, a here-string, `eval`, a variable as the program) is two-key. It flags more than it must: an interpreter's inline code, an unknown git subcommand and an email with keys the check doesn't read (attachments, threadId, from, headers) go to the owner rather than match.
- The second agent runs JSON-only with no tools, so it cannot look anything up; it works from the task context it is given.
- Two vendors agreeing on a wrong action is not detected.
- `request_approval` is advisory (L2). The hub runs nothing itself: the agent does the action after the answer. An agent that has its own connector (its own Gmail or CRM login) can label a send as something else, or skip asking, and the hub cannot see that. The check protects the paths that go through the hub (its MCP tools, Claude Code's `approval_prompt`, the ACP permission callback, the file broker). An agent that must not send on its own should not hold the credential.
- The ACP adapter cannot be handed draft B. A B pick is denied for it.
