## Unreleased

- **Simple by default: home, live strip, Advanced, delete room:** the apps open on a calm home instead of a flat list of everything. The home is a greeting, one box that asks "What do you want to get done?" (sending it starts a goal in the room you last worked in, or offers to make one), the rooms as cards with a one-line what's-happening, an "In progress" list of running goals with their live status, and a New room action. Above the conversation and the home sits a slim **live strip**: what is running right now (agent and task), approvals waiting (one tap to review), and each agent's usage left as a small dot chip (green/amber/red with "plenty / getting low / almost out / out until… / unlimited / learning") from `GET /agents/usage`; tapping a chip opens that agent's per-subscription windows. The everyday nav is now just Home, the conversation, Agents and Approvals; everything else (Memory, Permissions, Folders, Control files, Subscriptions, Remote, Personas, Résumés, Scorecard, Approval rules, Office, Issues, Appearance) moved behind one **Advanced** entry, and Approvals stays one tap away with a count whenever any is pending. The ⌘/Ctrl-K palette still reaches every screen by name. A room now has a quiet **Delete room** action (phone: room info; Mac: room settings) with a confirm; it calls `DELETE /rooms/:id`, and when work is running it shows the hub's message and offers "Stop and delete" (`?force=1`). Phone: `packages/hub/web/app.js` + `app.css` (home, `#strip`, usage detail, Advanced); Mac: `screens/HomeScreen.tsx`, `components/LiveStrip.tsx`, a reorganised `Sidebar.tsx` with an Advanced section, delete in `RoomSettings.tsx`, `Hub.usage()` and `Hub.deleteRoom(id, force)`. Tests: new default-nav and delete-room checks in `packages/hub/test/phone-app.test.ts`; the Night-shift and room-info UI tests now reach their screens the new way. Browser check `packages/hub/test/e2e/home.e2e.mjs` (demo in `home-demo.ts`); screenshots `docs/screenshots/home-*.png`, `room-with-strip-390.png`, `advanced-menu-390.png`, `usage-detail-390.png`, `delete-room-confirm-390.png`.
- **Save relay for off-machine agents:** an agent that runs on another machine (like Muse over Tailscale) can now do a task that works on the task folder, so every platform is used, not only this Mac's agents. A workspace task with no command check that has to run locally is relay-eligible: the off-machine agent gets a prompt that tells it to hand each deliverable file back in its reply as a `=== FILE: relative/path` ... `=== END FILE` block (relative paths only), and before judging the hub parses those blocks and writes the files into the task's own worktree through the same path guards every write uses (absolute paths, traversal and `.git` are refused), so the usual confinement, whole-deliverable judging and accepted-work merge all apply. The save is a distinct audited step (`task.save_relay`) with one quiet room line, and the saved files show as the task's changed files in Trace. A task whose checks must run on this Mac still goes only to a local agent, and an off-machine agent that hands back no file blocks for a file task is sent back once for the format instead of passing silently. New `packages/hub/src/placement/relay.ts` (eligibility predicate, block parser, guarded save); small hooks in the orchestrator, routing gate, plan owner rule and the task prompt; tests in `packages/hub/test/saverelay.test.ts`.
- **Usage left (hub):** `GET /agents/usage` answers how much each enabled agent has left, from the quota numbers the hub already keeps (ledger, subscriptions, 5-hour and weekly windows, learned limits, reset times a CLI printed). Per agent and per subscription: name and plan, each window's used tokens and runs, limit (the owner's or learned), whole-number percent left and reset time, and a plain status: "plenty" (more than 40% left), "getting low" (40% to 15%), "almost out" (under 15%), "out until 3:15 PM" (a reported or estimated limit, with `outUntil`), "learning your limits" (no limit known yet, never a made-up percentage) and "unlimited" for a local or free tier such as Hermes on Bonsai. An agent shows its best subscription, since it can run while any one has room. New `packages/hub/src/quota/usage.ts`; types in the "Usage-left per agent" section of `packages/shared/src/index.ts`; tests in `packages/hub/test/usage.test.ts`. No app screens yet.
- **Delete a room (hub):** `DELETE /rooms/:id` now removes everything the room owned, not just the room: goals, tasks, messages, routing rows, approvals, documents, memory and memory proposals, reply turns, goal steps, forks (and their lanes), pending file write-backs and the read mark, in one transaction, and its goal worktrees go through the existing clean-up. It refuses with a plain 400 while a goal is running or planning or a task is in review or revising, unless `?force=1`, which stops the room first. A DM room can be deleted like any other; the last channel cannot. The answer is `{ ok, counts }`, the audit line `room.deleted` names the room and what was removed, and clients still get `room_deleted`. Nothing on disk outside the hub's own data is touched (not the control folder, not a granted folder), and history about agents (usage, scores, lessons, juries, two-key records) stays. New `packages/hub/src/rooms/delete.ts`, `Store.deleteRoom`; tests in `packages/hub/test/deleteroom.test.ts`. No app screens yet.
- **Projects stop hanging:** three loops the owner's real runs hit are closed. A model provider's own safety or usage refusal (Anthropic "safeguards flagged this message", an OpenAI usage-policy refusal) is now told apart from the agent's own words, a placement block and a rate limit: it never counts an attempt or retries the same model. The task is tried once on an agent from each other model family, and if every ready family refuses (or only one is available) it is parked for the owner on the waiting path with one plain room line, so the goal does not spin or replan in a loop. The reviewer is now shown the whole deliverable (an ordinary report, plan or source file is no longer cut at 6000 characters), so a judge can confirm a criterion whose evidence sits late in the file instead of sending good work back forever; only a pathologically huge file is capped and labelled. When a reviewer's own reply can't be read, that is the judge's fault, not the worker's: a second reviewer is tried, and if it is also unreadable the task is decided from the runnable checks and the agent's self-report, or parked for the owner when there is nothing to go on, and never sent back as a revise that spends the worker's attempt. New `isProviderRefusal` in `packages/hub/src/orchestrator/failures.ts`, a larger judge budget in `ledger.ts`, and provider-refusal and unreadable-judge handling in the orchestrator; tests in `packages/hub/test/refusal.test.ts` and `packages/hub/test/judge-deliverables.test.ts`.
- **Durable goals:** a hub restart mid-goal no longer loses or repeats work. Every orchestrator step that changes a goal is written to a new `goal_steps` table (goal, task, step, time, and the data needed to resume: the agent, a finished run's reply, the verdict) before the change counts as done, in the same transaction as the task row it changes. On start, each running goal resumes from its last completed step: a run in flight is retried once and not counted as an attempt (or against the goal's run budget), a finished run whose reply was logged goes straight to judging, accepted work that was logged but not merged is merged, and a task that was already accepted never runs again. A plan that was still being written starts over without leaving half-saved tasks, and a goal waiting for plan approval or an answer from you keeps waiting. The room gets one quiet line per resumed goal. Resuming is safe to repeat: a step of a run is written once, recovering twice does not drive a goal twice, and a reply already posted before the stop is not posted again. The old "Picked up where we left off" line and the "hub restarted" history note are now "Picked up where it left off after a restart: N tasks done, M resumed." and "interrupted by restart". New code in `packages/hub/src/durable/`; tests in `packages/hub/test/durable.test.ts`.
- **Trace and Issues:** every goal now has one readable trace (`GET /goals/:id/trace`): plan and approval, tasks in plan order, each attempt with agent, model, time, tokens, outcome, failure tag, judge and score, and the approvals, reply turns and posts from that attempt, helpers under their parent, plus a short summary. `GET /issues` groups problems from the last 7 days (the same failure by the same agent or task type, repeated "couldn't reply", agents blocked by their environment, repeat posts kept out, approvals left waiting) into named issues with trace links and one next step; Dismiss keeps one hidden until it recurs with new evidence. Phone: a Trace button on the goal card and Issues in Settings. Mac: a Trace panel on the goal card and Issues in the sidebar. Nothing new is stored except the dismissals.
- **Office, live operations floor:** the office is now a dark, neon, isometric floor (three.js 0.170, no new files vendored). Each agent sits at its own glowing desk round a holographic pedestal for the goal: an original figure in the agent's colour (visor, headset, arms) that types, looks around, raises a hand under a pulsing amber beacon while it waits for approval, leans back under an orbiting gavel and scale while its work is judged, and dims with its monitors off when offline; its monitors show its real task title and a scrolling log of its latest lines. Helpers stand beside the parent's desk. A mission board ("Done means", with ticks and a progress ring) and a task-flow board (the goal's tasks as nodes in plan order, with moving dots on the connector into each task in progress) stand on the walls. Light trails run on the floor while agents work, and the page fires one-shot effects from what changed between two `/office` answers: a comet from the pedestal when a task is assigned, to the judge when work goes to review, a green burst when a task is accepted, a red pulse when it is sent back, an amber comet to the door for a new approval. Header: `<room> // Office`, agents, tasks, in progress and blockers, Live, 3D/2D, Full screen, Low power. Name tags (name and role) and status chips float over the desks. Click an agent for the inspector (role and bio line, current task with progress, start time and step, next step, blocked by, helpers, recent outputs, approvals, Open thread). Drag to turn, scroll or pinch to zoom toward the pointer, double-click to reset. The 2D plan (8 GB, no WebGL, phone upright) carries the same boards, counts and inspector. Dark by default; `?theme=light` or Appearance Light gives a light variant. `GET /office` adds `counts`, `goal.title`, `goal.tasks` (plan order with status, assignee, dependencies, judge), `goal.nextAction`, and per agent `role`, `about`, `task` (`startedAt`, `attempts`, `step`, `blockedBy`, and `progress` from criteria or the agent's usual time when known), `next`, `outputs`, `log` and `approvals` (`packages/hub/src/office/floor.ts`). The 3D scene moved to `web/office-scene.js`, fetched only for 3D. Pace: about 30 frames a second while agents work, 10 when nothing happens, none in low power. Browser check rewritten (27 checks, no console errors or CSP violations); screenshots `docs/screenshots/office-*.png`. Clicking an agent now opens the inspector; its Open thread button opens the DM as clicking used to.
- **Tasks that agents can actually do:** the planner and every task prompt now say an agent can create files only inside its task folder, with relative paths; a plan that tells a task to write to `/tmp` or another absolute path goes back to the planner once and is rewritten to a relative path if it is still there. The hub records where each external MCP agent connects from (loopback is this Mac; a Tailscale address or a proxied call is elsewhere; `location: "here" | "elsewhere"` on `PUT /agents/:id` overrides it), and a task that works on its folder (the new `workspace` need, set by the planner or worked out from files, command checks and file hand-backs) goes only to agents that run on this Mac, in routing, replacement tasks, helpers and night-shift re-runs. Such an agent gets text-only work and a prompt without a task folder; when no agent on this Mac is available the room gets one plain line. A replacement or fix task is skipped, with one quiet line, when every requirement it covers is already met by an accepted task. An agent that says it is blocked by its sandbox or environment ("cannot be created in this environment") gets the new `placement` failure tag, and the room line says it is a placement problem, not a quality one.
- **Reply turns:** every reply the hub asks an agent for (a DM, a tag, a roll call, a question from another agent) is one logged turn with one reply. A post made with the MCP tool during the turn is the reply and the final answer isn't posted again; a second post is kept out and counted; one message never asks the same agent twice; a post without a room goes to the room the agent is answering in. A roll call ends with a tally ("Roll call: 4 of 5 answered. Gemini didn't (...)"), and `GET /rooms/:id/turns` is the full log.
- **Room folders:** a room can have a default folder. Add one from the room's settings on the Mac (the native folder chooser, now built into the app) or make an existing folder the default; goals started in the room work on it, and **No folder** is still one tap in the composer. Removing a folder grant clears it as any room's default. The phone's room info lists the folders with **Make default** and **Remove from room**. Hub: `PUT /rooms/:id` takes `folderGrantId` (null clears), and `POST /rooms/:id/messages` treats `folderGrantId: ""` as no folder. Apps that send nothing now get the room's default.
- **Roll call:** `@all` (also `@everyone`, `@here`), or a short message like "have each agent respond", makes every connected agent in the room answer in turn instead of planning a goal that one agent answers. Agents that can't answer are named. Tagged agents now answer one after another in the order tagged (they used to run at once).
- **Mac app fixes from the first real build:** codesign could not read the entitlements (a `--` inside an XML comment); the office and the sign-in screen crashed on React Native's partial URL APIs; the build now runs `pod install` when the app's native dependencies change; a hub left running from an older build is restarted, and the hub works from its data folder, so Codex no longer fails with "Error loading configuration"; the DMG step ejects an earlier DMG still open in Finder; minimum macOS is 14 (D10).

- **4.2:** learned approval policy and permission leases. - **3.3:** subagents across the platform. - **4.6:** A2A agent card and an ACP adapter. The Room publishes `GET /.well-known/agent-card.json` (name "Agent Room", the tailnet name or the Funnel URL, the version from `VERSION`, a "run a goal" skill plus one per room command, bearer auth) and answers `POST /a2a` (JSON-RPC: SendMessage and `message/send` start a goal in a room, GetTask and `tasks/get` return its status, final summary and Library files, CancelTask and `tasks/cancel` stop it; the v1.0 and v0.3 spellings both work). - **3.2:** personas. Each agent's `SOUL.md` (name, colour, avatar, role, tone, bio) is editable in the Mac app (a Persona section on the agent card) and on the phone (Settings, Personas), with six starter templates (Analyst, Builder, Editor, Researcher, Operator, Skeptic). `GET` and `PUT /agents/:id/persona` and `GET /personas/templates`: a save is checked by the SOUL.md linter (its message comes back on a refusal), written as an owner commit through the control folder (or kept in the agent's record without one), and name, colour and the new avatar letter or emoji follow to every screen. The persona goes last in every prompt that makes text the owner reads (tasks, direct and tag replies, the final report, MCP assignments; Claude Code and Codex get it from their context file) between the persona markers, with "Voice only. The task, scope and rules above always win." Judges never see it: `judgePrompt` strips persona blocks from the reply and files, also when the jury is off or falls back to one judge, and `RESUME.md` never carries persona text. Code: `packages/hub/src/persona/`. Notes: `CONTROL.md` section 10.
- **2.3:** résumés and probation. The orchestrator keeps `agents/<id>/RESUME.md` from each agent's graded runs in the routing log: per task type the runs, mean quality, first-pass acceptance, send-backs, the failure-tag mix, jury agreement, the owner's spot ratings, model versions seen and the top lessons. Strengths and weaknesses are short lines that carry their numbers ("Strong on coding: 0.86 over 14 runs, 79% first-pass"; "Weak on writing: sent back 4 of 4 for verification (0.63 over 8 runs)"). Thresholds (`resume/tuning.ts`, also written at the end of every file): a type needs 3 graded runs; strong is 0.80 quality and 70% first-pass; weak is under 0.60 or half its tasks sent back; when the current model version has 3 runs of its own the line is about that version alone (2.4). The file is rewritten after graded runs at most once a minute per agent (one trailing write catches the rest) and at the end of every goal, by `orchestrator`; text under `## Owner notes` is kept; over 80% of 8 KB it is condensed (front matter never cut). The latest résumé is also kept in the database, so it works with no control folder. The planner sees each agent's strengths and weaknesses lines and who is on probation instead of the raw score table (capped per agent); RESUME.md is never put in an agent's task prompt or context file. A new agent (`POST /agents`, discovery) starts on probation; the seeded and demo agents, and agents that already have `probationRuns` (setting, default 5, 1 to 50) graded runs, do not. While on probation an agent is never the planned owner, never picked by learned routing, never offered to the planner (unless every connected agent is new: then nobody is held back). When a real task starts, each free probation agent that the capacity governor and quota admit gets a shadow copy: same prompt, own git worktree, judged like real work (jury when available), scored on its record (routing kind `shadow`, `shadow: true`), then discarded. A shadow run is never merged, adds no task, ledger line or room message (one quiet work-log line when judged), cannot ask for approval (every request is refused and audited as `shadow.denied`), post, ask another agent, save a document, propose memory or propose a file write. At the threshold probation ends with one line in the room ("Muse finished probation: 0.78 over 5 shadow tasks"), an audit entry and a fresh RESUME.md. `GET /agents/:id/resume`, `GET /resumes`, `POST /agents/:id/probation {on}` (the owner ends or restarts it, audited). Mac app: a résumé section on each agent card with progress and an End probation button. Phone: Settings, Résumés. Code: `packages/hub/src/resume/`.
- **2.2:** blind cross-vendor juries. A task's chat reply is rewritten into a neutral voice before judging (a local model does it when one is ready, else an agent from another family than the worker's; persona blocks, signatures and sign-offs are stripped first, and a rewrite that drops a number or file reference is refused for the mechanical text; files the task wrote are judged as files). Three judges from three model families, none the worker's, one of them local (quota-limited agents skipped, a local judge must be admitted by the capacity governor), grade it in parallel with the usual judge prompt; the result is one normal judgment (median score, majority verdict, per-criterion majority with ties UNSURE, merged feedback, drift when two judges flag it). With fewer than three other families ready the single rotating judge runs as before and the record says why. Every judgment is recorded in the `juries` table (`GET /juries?taskId=`) with judges, families, rewriter, Fleiss' kappa over criteria, pairwise agreement and score spread; rating a judgment records each judge's and the jury's distance from the owner's rating and keeps `jury_calibration` (`GET /jury/stats`: jury, single-judge, same-family and per-family error, the data for the "juries are worse than the user" kill criterion). A split jury emits a `jury_split` store event and an audit entry (2.7 listens). Setting `jury: { enabled, size, requireLocal, minFamilies }`; the Mac app shows a chip per judge and the agreement under each task and a switch in Settings, and goal summaries (phone too) say how the tasks were judged.

- **2.6:** slash commands from agent skills. Discovery now also indexes what each agent can run: Claude Code skills, custom commands and plugin skills and commands, Codex custom prompts and skills, Hermes skills. They show as namespaced commands (`/claude:board-deck`, `/codex:review-pr`, `/hermes:web-research`) in a `/` palette in both apps (Room commands first, then one group per agent; type to filter; up, down, Enter and Escape on the Mac, tap on the phone), from `GET /commands`. Choosing one routes straight to that agent with no planning and invokes it the way that agent supports: Claude Code commands go in as `/<name> args`, its skills as "Use the <skill> skill", Codex prompts are inlined with `$1`..`$9`, `$ARGUMENTS`, `KEY=value` and `$$` filled in, Hermes is told to run its skill. The task keeps `command` and the routing log records reason `command`. An unknown `/command` gets a short reply with close matches and never reaches an agent; room commands stay unprefixed and cannot be shadowed. The planner prompt lists each agent's best-matching commands (capped). Code: `packages/hub/src/commands/`.
- **1.1 (hub):** local file access.
